# C++Builder 2007 + Indy 10.6.2: совместимость MAX-адаптера

Этот файл фиксирует фактическое окружение LanMon у Евгения: **C++Builder 2007**, в котором штатные Indy-компоненты удалены и установлена более новая **Indy 10.6.2**. Версия и API подтверждены по присланным generated headers (`IdGlobal.hpp` сообщает `10.6.2.0`).

## Что остаётся без изменений

Production-код под `__BORLANDC__` не использует STL-контейнеры и `std::string`:

- строки API — `AnsiString` (`MAX_TEXT`);
- списки входящих сообщений — `TList`;
- HTTP-заголовки — `TStringList`;
- временные UTF-8/CP1251 буферы — обычные `new[]`/`delete[]`;
- JSON parser хранит массивы и объекты через VCL-совместимые списки.

Portable `std::string/std::vector/std::map` остаются только в ветке `#else` для Linux CI и не компилируются BCB2007.

## Какой Indy API используется

Присланный обновлённый Indy 10.6.2 экспортирует:

```cpp
#include <IdHTTP.hpp>
#include <IdSSLOpenSSL.hpp>
#include <IdMultipartFormData.hpp>

TIdHTTP
TIdSSLIOHandlerSocketOpenSSL
TIdMultiPartFormDataStream
```

То есть transport должен собираться именно против `Id*` headers. Старые `InHTTP.hpp/InSSLOpenSSL.hpp` относятся к штатной поставке BCB2007 и для фактического окружения Евгения больше не являются целевыми.

## TLS 1.2

В присланном `IdSSLOpenSSL.hpp` есть явное значение:

```cpp
enum TIdSSLVersion {
    sslvSSLv2,
    sslvSSLv23,
    sslvSSLv3,
    sslvTLSv1,
    sslvTLSv1_1,
    sslvTLSv1_2
};
```

Поэтому transport задаёт TLS 1.2 напрямую:

```cpp
Ssl->SSLOptions->Method=sslvTLSv1_2;
```

Дополнительно код до первого HTTP-запроса проверяет OpenSSL runtime:

```cpp
LoadOpenSSLLibrary();
IsOpenSSL_TLSv1_2_Available();
```

Если DLL не загрузились или загруженная версия OpenSSL не умеет TLS 1.2, transport работает fail-closed и возвращает понятную ошибку.

Проверка сертификата MAX не отключается:

```cpp
Ssl->SSLOptions->RootCertFile=rootCert;
Ssl->SSLOptions->VerifyMode=TIdSSLVerifyModeSet()<<sslvrfPeer;
Ssl->SSLOptions->VerifyDepth=9;
```

При отсутствии `certs\\max-ca.pem` сетевой запрос также не выполняется.

## Проверка на машине Евгения

Сначала скомпилировать три файла `Max/api/*.cpp`, затем LanMon полностью.

После успешной сборки проверить:

1. `certs\\max-ca.pem` находится рядом с `lanmon4.exe` в подпапке `certs`.
2. Загружаются именно OpenSSL DLL, с которыми установленный Indy 10.6.2 умеет TLS 1.2.
3. `GetMe` возвращает информацию о MAX-боте.
4. `GET /updates` работает и marker продвигается.
5. Отправляется текстовое сообщение.
6. Отправляется картинка.
7. Отправляется документ.
8. Русский текст корректно проходит CP1251 → UTF-8 → CP1251.
9. При удалённом/испорченном `max-ca.pem` запрос завершается ошибкой.
10. При несовместимых OpenSSL DLL отображается ошибка загрузки/TLS 1.2, а не происходит небезопасный fallback.

## Автоматическая защита

`tests/test_bcb2007.py` проверяет, что Borland production path снова не получил STL и что transport остаётся совместим с присланным Indy 10.6.2 (`Id*`, `sslvTLSv1_2`).

Linux CI проверяет protocol/client, source contracts, реальный TLS 1.2 handshake с `platform-api2.max.ru` и E2E mock. Он всё равно не заменяет финальную компиляцию `bcc32`: окончательное подтверждение ABI — сборка на машине с C++Builder 2007 + установленным Indy 10.6.2 + его OpenSSL DLL.
